# 给 workbuddy 的文档能否指导客户上线

| 项 | 内容 |
| --- | --- |
| 检查对象 | `docs/PRD-小程序全栈开发.md`（v1.0-agent） |
| 检查日期 | 2026-10-13 |
| 结论 | 能指导做出与当前原型一致、可本地跑通的微信小程序。不能指导上线给客户使用。 |

按该文档实现，客户拿到的是「广州 3 家永辉店、固定数据日期、拍照永远进入天娱广场店、全员共用 smartgo」的演示系统。文档第 0 节还禁止 Agent 改掉这些限制。

---

## 文档已经写清、Agent 可以照做的部分

- 10 个页面的信息架构、文案、空态和返回关系
- 门店、活动、建议、报告的字段契约
- 本地 API 列表与 SQLite 持久化
- 15 条演示一致性验收

这些足够让 workbuddy 复刻原型，不足以交付给一线客户日常使用。

---

## 挡住上线的缺口

### 1. 交付目标写成了本地演示

文档写明交付形态是「微信小程序 + 可本地运行的后端」，接口建议跑在本机 `8787`。没有生产域名、HTTPS、环境划分、发布步骤、备份和故障处理。微信小程序上线还缺：小程序主体与类目、服务器域名白名单、用户隐私保护指引、相机权限说明、提审材料。按当前文档做完，无法提交给客户安装使用。

### 2. 账号不能给真实组织用

全系统只有 `smartgo` / `smartgo123`，密码写在需求正文里。登录后的人可以同时进 DSR、总部、导购。总部动态里的李倩、王磊是写死名单，不会随真实拜访变化。没有入职开通、离职停用、密码重置、片区权限和操作审计。

### 3. 经营数据不能随客户业务更新

数据被钉死为 2026-08-31、广州 3 店。昨天 / 近 7 天由近 30 天推算，首页 ROI 是写死的 `8.46`。没有从 StoreVerse 拉归一门店、订单、机制、POI 的同步任务，也没有数据日期过期时的提示。客户第二天打开，看到的仍是同一天的三家店。

### 4. 识店和建议都不是现场能力

拍照三步动画结束后固定进入天娱广场店，文档禁止接入真实识别。搜索只能命中这 3 家。建议正文来自种子文案，文档禁止在线生成。客户到一家新店，得不到这家店的看板，也得不到依据当天数据写出的建议。

### 5. 采纳没有客户可执行的下游

采纳只改报告状态，可配券线索等于采纳条数。没有工单、计划或配券申请，总部不能据此派活。状态不能撤销，也没有通知。客户会认为「采纳了却没有下一步」。

### 6. 验收测的是演示还原，不是上线

15 条验收全部在核对三店数字、固定文案和动画。没有覆盖：多人同时使用、权限隔离、数据刷新、错误密码锁定、接口超时、小程序真机相机权限、提审前隐私弹窗。Agent 全部打勾，仍然只证明演示复刻成功。

## 补成上线文档之前需要先拍板的问题

下面没定之前，不适合改写实现规格，否则 Agent 会猜一套上线方案。

| 编号 | 要定的事 | 不拍板时 Agent 只能维持的现状 |
| --- | --- | --- |
| 1 | 第一批客户是谁，覆盖哪些城市和零售商 | 只有广州永辉 3 店 |
| 2 | 账号从哪来：现有工号系统，还是本系统自建 | 只有 smartgo |
| 3 | 总部、DSR、导购是否必须分权 | 登录后三个入口都能进 |
| 4 | 识店失败时是否允许只靠搜索，拍照是否必须真识别 | 拍照永远进天娱 |
| 5 | 看板数据是否接 StoreVerse 现成标签，更新频率是每天还是进店实时 | 数据日期永远 2026-08-31 |
| 6 | 建议是规则模板、人工预写，还是模型生成 | 只用种子里的 8 条建议 |
| 7 | 采纳之后总部要收到什么：仅记录、生成计划，还是发起配券申请 | 只增加一个数字 |
| 8 | 小程序主体、服务器和域名由谁提供 | 文档只要求本机可跑 |

这 8 项定稿后，再把 `docs/PRD-小程序全栈开发.md` 从「原型复刻规格」改成「客户上线规格」。在此之前，workbuddy 按现文档开发，交付物只适合内部演示。
